PAwR-NCS — Handoff Summary (2026-07-31)
Repo: https://github.com/alejandro3141592/PAWR-NCS.git (branch main, one commit so far)
Stack: nRF Connect SDK v3.3.0 (Zephyr), NOT PlatformIO despite the parent folder name. Built with west/CMake via the nRF Connect for VS Code extension (plain CLI west build has environment issues in this setup — see Gotchas).
Hardware: 2x Seeed XIAO nRF52840 (plain, not the Sense variant — confirmed via BOARD:STRING=xiao_ble/nrf52840 in the build cache), one running central/, one running peripheral/.

Goal
17 wearable peripheral nodes, each reading skin temperature (MAX30205) + humidity/sweat-rate (SHT4x) over I2C, reporting to one central hub every 10 seconds via PAwR (Periodic Advertising with Responses). Central just prints received values for now — no storage/processing yet.

Architecture
central/src/main.c — the PAwR advertiser/hub. Runs periodic advertising (20 subevents, 1 slot each, 10s interval), dynamically assigns each peripheral a subevent over a GATT write during onboarding (connect → PAST → discover → write → disconnect, repeats forever), parses responses into struct sensor_payload and prints them.
peripheral/src/main.c — the PAwR sync/responder. Advertises connectable, receives PAST from central, syncs to the periodic train, reads sensors every 10s via a k_work_delayable, responds to its assigned subevent's poll with the latest reading. Has a status LED (led0, red): off = not synced, steady on = synced, brief blip = response sent.
common/pawr_protocol.h — single source of truth, included by both apps. Defines NUM_SUBEVENTS=20, timing constants (PAWR_INTERVAL_UNITS=10s, PAWR_SUBEVENT_INTERVAL, etc.), and the 8-byte struct sensor_payload wire format (node_id, flags, seq, temp_cdeg, humidity_pct10). Any timing/payload change must be made here, not duplicated in either app.
peripheral/boards/xiao_ble.overlay — devicetree overlay adding sht4x@44 (Sensirion, humidity) and max30205@48 (via the LM75-compatible in-tree driver, temperature) on &i2c1. Also overrides the board's i2c1_default pinctrl to add bias-pull-up (see Fixed Issues #2).
peripheral/Kconfig — CONFIG_APP_NODE_ID (1-17, human-readable label only, does NOT drive subevent assignment) and CONFIG_APP_SIMULATE_SENSORS (fake sensor values for protocol-only testing without hardware).
lib/ — gitignored, not in the repo. Old Arduino/Bluefruit broadcast-based reference from before the PAwR migration (different BLE stack entirely, kept locally only for historical context). Don't port code from it directly.
Fixed this session (chronological, all confirmed working except where noted)
Sensor devicetree overlay wasn't being picked up — filename auto-discovery failed silently for this board's qualifier resolution; fixed by referencing the overlay explicitly via set(DTC_OVERLAY_FILE ...) in peripheral/CMakeLists.txt before find_package(Zephyr). Any build that doesn't show sht4x@44/max30205 in the generated zephyr.dts means this broke again — check that first.
Humidity always read 0.0% / SHT4x device_is_ready() false — root cause was the board's i2c1_default pinctrl not enabling the SoC's internal I2C pull-ups on the exposed header pins, while Arduino's Wire.begin() does by default on the same hardware (confirmed by re-testing the working Arduino sketch on identical wiring — ruled out a physical/wiring fault). Fixed by overriding i2c1_default in the overlay with bias-pull-up. Confirmed working — user saw real readings (37.5%, 63.9%) after this fix. (I2C bus speed was also dropped from fast/400kHz to standard/100kHz during debugging as a red herring — didn't fix it alone but kept since it matches the Arduino reference.)
skip=1 in peripheral's PAST subscribe was adding a full unnecessary 10s of latency before the first sync attempt at the new 10s interval (the original NCS demo's skip=1 made sense at its much shorter interval). Changed to skip=0.
Peripheral's sync-wait timeout too short / retry-while-still-connected -ENOMEM — widened the wait to PAWR_INTERVAL_MS * 2 and added proper wait-for-disconnect-before-retry logic (sem_disconnected) so the peripheral doesn't try to re-advertise while still connected to central (CONFIG_BT_MAX_CONN=1 has no headroom for a second connection object).
Central handed out a brand-new subevent slot on every reconnect from the same physical peripheral (no identity tracking, just "first free slot") — fixed by keying slot assignment to the peripheral's Bluetooth address (bt_conn_get_dst) via a new slot_owner[] table, so a peripheral that fails to sync and retries gets its same slot back instead of leaking a new one each attempt.
0x08 (CONN_TIMEOUT) disconnects, suspected radio contention — central's onboarding GATT connection used the library default (30-50ms interval / 4s supervision timeout), which may be too tight now that central's radio is also servicing a much busier periodic advertising train (20 subevents/10s) than the original demo (5 subevents, 319ms interval). Widened to a custom 100-150ms interval / 10s timeout (onboard_conn_param in central/src/main.c). Not yet confirmed fixed — was applied in the same round as the slot-identity fix (#5), no fresh test results yet.

Design decisions already made (don't relitigate without reason)
Dynamic, hub-driven slot assignment (central assigns via GATT write) was chosen over fixed compile-time node IDs, specifically because the user wants future support for slot-shifting and flexible node-count membership — this required keeping the full connect/PAST/discover/write onboarding flow rather than simplifying it away.
No app-layer CRC on the sensor payload — BLE already CRCs every PDU at the link layer, redundant for a same-room print-only receiver.
Fixed-point wire format (int16_t temp_cdeg, uint16_t humidity_pct10), not float, to avoid float-in-BLE-payload portability questions.
Real Zephyr sensor drivers used throughout (sensirion,sht4x in-tree, MAX30205 via the register-compatible in-tree lm75 driver) — no Arduino libraries needed or used.

PAwR Skin Sensor Project — Handoff Summary
Repo: https://github.com/alejandro3141592/PAWR-NCS.git (branch main)
Stack: nRF Connect SDK v3.3.0 (Zephyr), built with west/nRF Connect for VS Code extension — not PlatformIO despite the folder name. Board: Seeed XIAO nRF52840 (plain, not Sense — confirmed via BOARD=xiao_ble/nrf52840).

Goal
17 wearable peripheral nodes reading skin temperature (MAX30205) + humidity/sweat proxy (SHT4x), reporting to one central hub every 10s over Bluetooth PAwR (Periodic Advertising with Responses). Central just prints received readings for now.

Architecture
central/src/main.c — the PAwR advertiser/hub. Runs periodic advertising (20 subevents, 1 response slot each, 10s interval), scans for peripherals named "PAwR sync sample", connects, sends PAST (Periodic Advertising Sync Transfer), does GATT discovery, writes each peripheral a {subevent, response_slot} assignment, disconnects, repeats forever. Assignment is dynamic/hub-driven by design (not baked into peripheral firmware) so future work can add slot-shifting and flexible node-count membership without redesigning the onboarding channel.
peripheral/src/main.c — the sync/responder. Advertises connectably, receives PAST, syncs to central's periodic train, reads MAX30205+SHT4x every 10s via a k_work_delayable, answers every subevent poll for its assigned slot with the latest reading (sent as BT_DATA_MANUFACTURER_DATA).
common/pawr_protocol.h — single source of truth, included by both apps. Has the struct sensor_payload wire format (8 bytes: node_id, flags, seq, temp_cdeg, humidity_pct10) and all PAwR timing constants (NUM_SUBEVENTS=20, PAWR_INTERVAL_MS=10000, etc). Any protocol/timing change must go here so both sides stay in sync — this is the #1 thing to keep in mind when either of you touches central or peripheral.
peripheral/boards/xiao_ble.overlay — devicetree overlay adding sht4x@44 and max30205 (via the LM75-compatible in-tree driver) on &i2c1, plus a critical bias-pull-up override on the i2c1_default pinctrl group (see Fixed Issues below).
peripheral/Kconfig — app-local CONFIG_APP_NODE_ID (1-17, human-readable label only, does NOT determine subevent assignment) and CONFIG_APP_SIMULATE_SENSORS (fake sensor values for protocol testing without hardware).
lib/ — not in the repo (gitignored). Old Arduino/Bluefruit broadcast-based reference from a different, incompatible BLE stack. Concepts were mined for the payload design; code is not reusable.
Issues found and fixed this session
Devicetree overlay wasn't being auto-discovered — fixed by explicitly setting DTC_OVERLAY_FILE in peripheral/CMakeLists.txt rather than relying on boards/<board>.overlay filename convention (which wasn't matching for this board's qualifier resolution). If you ever rename/move the overlay file, update that CMakeLists.txt line too.
Humidity always read 0.0%, flags showed HUMIDITY_INVALID — root cause: the board's i2c1_default pinctrl doesn't enable the SoC's internal I2C pull-ups on the exposed header pins, unlike Arduino's Wire.begin() which does by default on the same hardware. Confirmed via a working Arduino reference sketch on identical wiring. Fixed with a bias-pull-up override in the overlay. This is now working (confirmed reading real values like 37-64% RH).
-ENOMEM / advertising-restart race — peripheral was retrying connectable advertising while still connected to central (only 1 connection slot available). Fixed with a sem_disconnected semaphore so the retry loop waits for actual disconnection first.
PAST skip=1 was adding a full unnecessary 10s of latency before the peripheral's first sync attempt, given the periodic interval is now 10s (the original NCS demo's skip=1 made sense at its much shorter interval). Changed to skip=0.
Slot allocation had no peripheral identity — central handed out a brand-new subevent slot on every reconnect from the same physical peripheral (0→1→2...) instead of recognizing it as the same device. Fixed by keying slot assignment to the peripheral's Bluetooth address via bt_conn_get_dst().
LED indicator added on peripheral's led0 (red): off = not synced, steady on = synced, brief blip = response sent. (Central already had a TX-toggle LED on led1 from the original demo.)
Possible radio-contention fix: central's onboarding connection now uses slower/more tolerant parameters (100-150ms interval, 10s supervision timeout vs the library default 30-50ms/4s), since the default was suspected to be too tight given the radio also has to service the much busier periodic advertising train now (20 subevents vs the demo's 5).
Unresolved / what to pick up next
Periodic sync has never actually succeeded once ("Periodic sync established." has not appeared in any log yet), despite fixes #3, #4, #7 above. Central completes its whole sequence (PAST sent → Discovery started → Write started → PAwR config written) and disconnects cleanly, but the peripheral times out waiting for sync_cb to fire every time. This is the main open bug. Next diagnostic steps:

Get fresh logs from both sides simultaneously (same test run) after fix #5 (address-keyed slots) — confirm the same peripheral now keeps the same subevent number across reconnects instead of drifting.
If sync still never establishes even with a stable slot: the remaining suspects are (a) the connection-parameter/radio-contention theory not being fully correct, (b) some other PAST/periodic-sync timing issue specific to the 10s interval configuration, or (c) something in the extended/periodic advertising parameters themselves. Worth testing with a much shorter debug interval (e.g., temporarily drop PAWR_INTERVAL_UNITS back to something like the original demo's 0xFF in common/pawr_protocol.h) to isolate whether the 10s interval itself is the variable causing sync to fail, versus something else.
Central and peripheral logs both need timestamps ideally (peripheral's app-level printk lines currently have none, only the early boot lines do — makes it hard to tell how much wall-clock time elapsed between events).
Build/flash notes
